### Category 2: Build-once identity
**Evidence: Inconsistent across paths. Each path that builds a CLI artifact rebuilds from source on its own runner.**

- `release.yml`: identity = git tag + plan manifest (`dist plan ... --output-format=json` at L78-83); `BUILD_MANIFEST_NAME` env var at L114
- `agileplus-release.yml`: identity = `$GITHUB_REF_NAME#v` (L61) + matrix target; no lockfile pinning (`cargo build --release` at L55, no `--locked` flag)
- `release-crates.yml`: identity = tag `v*`; no `--locked` flag
- `release-plz.yml`: identity = git head of merged release-plz PR + `merge_commit_sha`; no `--locked` flag
- `release-attestation.yml`: identity = `${{ github.sha }}` (in BUILD_MANIFEST.txt L66); uses `--locked` (L44)
- `release-desktop.yml`: identity = tag; uses `Swatinem/rust-cache` with shared key

**Verdict: NOT BUILD-ONCE.** 4 of 6 paths that build the CLI do not pin the lockfile. cargo-dist (release.yml) does NOT use `--locked` either — it relies on dist's own manifest. Artifact identity is determined by the path that built it; no shared content-addressable identifier across paths.

**Specific evidence anchors:**
- `.github/workflows/release.yml:42-46` (tag trigger)
- `.github/workflows/agileplus-release.yml:55` (no `--locked` on `cargo build --release`)
- `.github/workflows/release-crates.yml:26, 41` (no `--locked` on publish commands)
- `.github/workflows/release-attestation.yml:44` (`--locked` is the only path that pins it)

### Category 3: Candidate-bound approval
**Evidence: No explicit candidate-bound approval gate. Manual `workflow_dispatch` is the only "approval".**

- `release.yml`: triggered ONLY by tag push — tag is the approval (no separate gate)
- `agileplus-release.yml`: `workflow_dispatch` only — anyone with `contents: write` can fire it; **no environment protection, no required reviewers**
- `release-crates.yml`: triggered by tag push — tag is the approval
- `release-plz.yml`: triggered by main push or merged release-plz PR — PR merge is the approval
- `release-attestation.yml`: triggered by `release: published` event or `workflow_dispatch` — release creation is the implicit approval
- `promote.yml`: calls `gate-check.yml` for risk-profile gating, **but gate-check.yml does not exist** — promote.yml is currently non-functional (will fail at workflow resolution)

**Verdict: APPROVAL-VIA-TRIGGER, NOT APPROVAL-VIA-GATE.** No environment protection rules visible in workflows; no `production` / `release` GitHub Environment usage. The "approval" for a release is the act of pushing a tag or running a manual dispatch, not a human review of the candidate. `.mergify.yml` is for PR auto-merge only (8 rules, PR context).

**Specific evidence anchors:**
- `.github/workflows/agileplus-release.yml:5-7` (workflow_dispatch without environment gate)
- `.github/workflows/promote.yml:40` (broken `uses: ./.github/workflows/gate-check.yml`)
- `.mergify.yml:1-83` (PR auto-merge rules, no release context)

### Category 4: Terminal-success requirements
**Evidence: Each path has its own terminal gate. No shared "all-must-pass" gate.**

- `release.yml`: host job gate at L221 — `if: ${{ always() && needs.plan.result == 'success' && needs.plan.outputs.publishing == 'true' && (needs.build-global-artifacts.result == 'skipped' || needs.build-global-artifacts.result == 'success') && (needs.build-local-artifacts.result == 'skipped' || needs.build-local-artifacts.result == 'success') }}`
  - Allows skipped results (for prereleases), requires plan to be success, requires build results to be success-or-skipped
- `agileplus-release.yml`: `github-release` and `publish-crates` both `needs: build-matrix` (L108, L129)
- `release-crates.yml`: dry-run on PR, publish on tag push — terminal gate is just "tag pushed" (no upstream CI)
- `release-plz.yml`: `release-pr` and `publish` are independent jobs gated by event type
- `release-attestation.yml`: triggered post-release; not part of any gate
- `promote.yml`: `publish` job `needs: gate-check` — but gate-check.yml is missing

**Verdict: PER-PATH, NO AGGREGATE GATE.** Each workflow can succeed independently. There is no single "release gate" that requires, e.g., lint+test+security+attestation all pass before ANY release path fires. The closest is the Mergify PR auto-merge (`.mergify.yml:6-19`) which requires `ci`, `lint`, `test` to be success.

**Specific evidence anchors:**
- `.github/workflows/release.yml:221` (host job terminal gate)
- `.github/workflows/agileplus-release.yml:108, 129` (per-job `needs`)
- `.mergify.yml:6-19` (PR-side gate)

### Category 5: Exact-byte promotion
**Evidence: Multiple paths rebuild from source. None use exact-byte promotion (i.e., download-artifact → upload-publish).**

- `release.yml`: `host` job does `actions/download-artifact@v8 pattern: artifacts-*` (L240-244) then re-runs `dist host` (L248) — this IS within the same workflow run, so artifacts are exact-byte promoted
- `agileplus-release.yml`: `github-release` does `actions/download-artifact@v8` (L114-117) then publishes — exact-byte within same run
- BUT `release-attestation.yml` REBUILDS from source after the release is published (L40-44: `cargo build --release --locked --workspace --all-targets`) — **NOT exact-byte**, the attestation covers a different binary than the release
- `release-crates.yml`: rebuilds per-tag; uses `--allow-dirty` (release-plz) or just `--token` (release-crates)
- `release-plz.yml`: rebuilds at publish time; `--allow-dirty` flag documented in inline comment as workaround for release-plz/action#14
- `publish.yml` (reusable): `mise run build` then `cargo publish` — rebuilds

**Verdict: MOSTLY EXACT-BYTE WITHIN A RUN, EXCEPT ATTESTATION.** `release.yml` and `agileplus-release.yml` are exact-byte within a single workflow run. `release-attestation.yml` rebuilds for attestation, which is a real divergence from the released artifacts.

**Specific evidence anchors:**
- `.github/workflows/release.yml:240-244` (download-artifact pattern: `artifacts-*`)
- `.github/workflows/agileplus-release.yml:114-117` (download-artifact with `merge-multiple: true`)
- `.github/workflows/release-attestation.yml:40-44` (fresh `cargo build --release --locked`)

### Category 6: Post-publish verification
**Evidence: NO post-publish verification gate anywhere in the release paths.**

- No smoke test job after release creation
- No install matrix (no "after release, install on a clean machine and run smoke")
- No signature verification step
- No `gh release verify` or similar
- `release-attestation.yml` only attests provenance; does NOT verify the released artifact against the attestation
- The only post-publish-adjacent job is `announce` in `release.yml` (L281-) which only generates release notes

**Verdict: NO POST-PUBLISH VERIFICATION.** The release is published, attested at best, and then nothing checks it actually works. `STABLE.md` defines the S0/S1/S2 tier criteria but these are not enforced as release gates — they are organizational tracking criteria.

**Specific evidence anchors:**
- `.github/workflows/release.yml:281+` (announce job: no verification, just notes)
- `.github/workflows/release-attestation.yml` (no verification step, only attestation generation)
