### The gitleaks failure was a checkout-depth bug, not a leak

`ci.yml`'s `security` job used `actions/checkout@v7` with the default
`fetch-depth: 1`. `gitleaks-action@v3` invokes git over the range
`prev_commit^..head_commit`, so the parent commit object must exist. It did not:

```
fatal: ambiguous argument '51be78be...^..eeebe131...': unknown revision or path not in the working tree.
failed to scan Git repository error="stderr is not empty"
WRN scanned ~0 bytes (0)
WRN no leaks found in partial scan
##[error]ERROR: Unexpected exit code [1]
```

No secret was ever present — the SARIF report was still produced and uploaded.

**A/B evidence, both directions:**

- FAIL: `eeebe131` (run 38655941910, job 116166422796) and `aedc4775`
  (run 38322660347, 2026-10-12, *before* this campaign) show byte-identical
  `fatal: ambiguous argument ... unknown revision`.
- PASS: CI runs 38533236788 (`dda62df4`) and 38540264394 (`e1c8b3e9`) show
  `1 commits scanned.` / `no leaks found`.
- Reproduced locally: in a `--depth 1` clone,
  `git rev-parse 51be78be^..eeebe131` returns the *same* fatal error; a full
  clone resolves it to `^45bb5c9f`. Fetch depth is therefore causally
  sufficient and necessary for this failure.
- Caveat: the local gitleaks binary is 8.30.0 versus CI's 8.24.3. 8.30 dropped
  `--first-parent` as a standalone flag and tolerated the bad range (1 commit,
  exit 0). The CI log is the authoritative evidence; the local repro
  corroborates only the git-level cause.

`gitleaks.yml` (line 27-28) and `security.yml` (line 56-57) already set
`fetch-depth: 0`, which is why only the `ci.yml` path was affected.

This also cleared `ci / lint` and `ci / test`, which aggregate the security
gate result.
